## 第七轮（补齐记录）：竖屏自适应 —— UI 上下适配 + 中部舞台跟随屏宽

> 这轮改动实际发生在 09-21 深夜 ~ 09-22 08:25（构建 k8v875），当时没来得及记，这里补齐。

需求原话：「屏幕适配的不是很合适，我们适配的竖屏，ui上下要做适配。中间跳板要跟随屏幕的宽带拉伸或者缩小来保证屏幕瓶子移动区域和履带在屏幕中间 然后就是影子一般是在最底层，然后是在瓶子的下方再上去一点」

**做法**（`GameRoot.applySafeLayout()`，每帧检测 `view.getVisibleSize()` 变化后重算）：

1. **设计区容器方案**（先试过 `ResolutionPolicy.SHOW_ALL`，超长屏两侧留黑不好，弃用）：
   `view.setDesignResolutionSize(720, 1280, FIXED_WIDTH)` + 外层 `contentRoot` 整体
   `s = min(1, vh/1280)` 缩放居中。屏幕高 ≥ 1280（真机竖屏）时 s=1，完全不生效，不留黑边。
2. **UI 上下适配**：`SAFE_BLOCKS = { topY 550, topBottomY 438, botTopY -234, botBottomY -530 }`。
   `hudDY = (vhE/2 - padTop) - 550`、`navDY = (-vhE/2 + padBottom) + 530`，
   分别作用到 `hudRoot` / `navRoot` / `drawerLayer`（抽屉必须跟着底部块一起走，否则盖住导航）。
   `padTop/padBottom = max(设计留白, 异形屏安全区)`；**安全区要用 `sys.getSafeAreaRect()` 除以 s 换算到设计等效单位**，
   否则 s<1（平板/宽屏）时顶部留白被算成巨大值、顶部 UI 块被推到屏幕底部（这个 bug 修过一轮）。
3. **中部舞台跟随屏宽**：新增 `WORLD_ENV = { x0:-364, x1:284, y0:-262, y1:440 }`（左侧履带 + 桌面 + 瓶子活动区的总包络）。
   `bandTop/bandBottom` = 上下 UI 块之间的剩余带；`ws = min(fitH, fitW)`（`fitW = vwE*0.97/envW`），
   `worldLayer.scale = ws`、`worldLayer.pos = (-envCX*ws, 带中心 - envCY*ws)`。
   → 于是「瓶子活动区 + 履带」整体**水平居中于屏幕、垂直居中于上下两块 UI 之间**，并随屏宽拉伸/缩小。
   实测：9:16 → ws 0.954；9:20 → ws 1.078（放大填满宽度）；平板/宽屏 s<1 → ws 0.952。
4. 面板顶部白条：`ui/panel_deco` 贴图本身接近白色，直接当标题背板是一条突兀白块 → 染 `#6E5A34` 压成暗金铭牌。
5. 抽屉遮挡导航：`LAYOUT.drawerClosedY` 从原来的值改到 `-752`（收起时抽屉头上沿落在导航下沿 -530 之下）。

## 本轮（09-22 上午）：影子贴地 + 桌腿贴板 + 四比例复验

### 1. 影子必须锚在「地面线」，不能跟着姿态补偿量 `restDy` 走（真实 bug，已修）

`Bottle.applyRest()` 原来写 `shadow.y = node.y - SHADOW_DY`，而 `node.y = homeY + restDy`：

- 贴图锚点是 `(0.5, 0.34)`（锚点在瓶底上方 0.34·H）；
- `poseOf('ok')`（瓶口朝上）给了 `restDy = 0.32·H`，**这个量正是用来抵消 180° 翻转后瓶底位置变化的**；

**修法**：`const shPos = new Vec3(tx, this.homeY - SHADOW_DY, 0)` —— 影子 y 只跟 `homeY`（地面线）走。

### 1. ★ 系统性渲染 bug：`Color.fromHEX(sp.color, '#..')` 就地改色**静默失效**（全 UI 中招）

**现象**：技能树 17 个节点无论锁定/可买/满级**渲染出来全是同一块土黄**，
只有图标和挂锁不同；导航高亮、页签选中、等级条/价格的红绿状态也全都不变色。
但 `sp.color.toHEX()` **读回来是正确的**，所以从代码上完全看不出来。

**根因**（Cocos `Renderable2D` 的 color setter 第一步）：
```ts
set color (value) {
    if (this._color === value) { return; }   // ← sp.color 取到的就是内部 _color 本体
    this._color.set(value);
    this._updateColor();                     // ← 于是这一句永远不会执行
}
```
`Color.fromHEX(out, hex)` 是**就地改写** `out`，引用没变 → setter 提前 return →
顶点色数组还是旧值 → GPU 用旧颜色渲染（= 贴图原色）。
构建期通过 `label(..., {color})` / `setFrame(sp,...,color)` 传新 Color **是走 setter 的**，所以初始色正常，
**只有运行时改色会失效** —— 这正是"看起来像美术配色没做完、其实是渲染没刷新"的原因。

**决定性验证**（值得复用）：同屏两个节点，A 用 `Color.fromHEX(sp.color,'#0000FF')` 就地改，
B 用 `sp.color = new cc.Color(0,255,0,255)`；截图采样 → A 是 `#BAB7A2`（贴图原色），
B 是 `#00B700`（正好 = `#BAB7A2 × #00FF00`）。**乘法染色只在走 setter 时生效。**

**修法**：`UI/UIKit.ts` 新增
```ts
export function tint(r: Sprite | Label, hexStr: string): void {
    const c = hex(hexStr);            // hex() 每次返回新 Color
    const cur = r.color;
    if (cur.r === c.r && cur.g === c.g && cur.b === c.b && cur.a === c.a) { return; }
    r.color = c;                      // 整体赋值 → setter 才跑 _updateColor()
}
```
并用脚本把 7 个 UI 文件里 **30 处** `Color.fromHEX(x.color, ...)` 全量替换成 `tint(x, ...)`
（`Core/Util.ts` 的 `hex()` 内部那处是新建对象，合法，保留）。
附带脚本自动把不再使用的 `Color` 从 cc 导入里删掉。
