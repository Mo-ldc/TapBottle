## 第四十三轮：瓶盖链路性能审计与优化（用户问帧率波动）
**实测手段（重要沉淀）**：CDP hook `Label.prototype` 的 `string` setter（defineProperty 包装）
按 `parent/name` 统计写入次数 —— 直接暴露「每帧写文本」的元凶；hook `Label.updateRenderData`
不生效（3.8 里该方法只在脏时被内部调用，别用它统计）。drawcall 读 `director.root.device.numDrawCalls`。

**审计结论**：drawcall 仅 47（瓶盖激活时 51）→ 渲染合批早已良好（瓶盖 110 个同图 Sprite
合批、文字层未破批），瓶颈全在 **CPU 侧的 Label 文本重写**：3 秒 1043 次 string 写入 =
每次都触发系统字体重排 + canvas 重绘 + 纹理上传。TOP 来源：
① `Abilities.refreshBar` 每帧写 3 个能力 Label（525 次）；
② `BottomPanel.refresh` 每 0.25s 无条件重写全部 UpgradeRow 文本（408 次）；
③ hintLb 32 次。

**修复（全部落地）**：
1. **文本先比对再写**：Abilities.refreshBar（put helper）、UpgradeRows.applyRow
   （name/sub/btnLb/lvLb）、BottomPanel.refreshHead（hintLb/msLb）、BottleField.sync
   的 overflowLb → 实测 1043 → **75 次/3s（↓93%）**，ab_* 每帧写入归零。
2. **HUD 金币数字节流**：缓动插值期间每帧写 string → 限 0.06s 一次（moneyTxtAcc）。
3. **CapMachine**：入账飘字同帧累加 + 0.35s 节流（80 枚入账从几十条降到 6 条）；
   binLb 在途数 0.12s 节流；染色改预建 Color 常量数组（原每颗 new Color）；
   acquire 加游标（均摊 O(1)）。
4. **G.notify 同批合并**：首次调用仍同步广播（语义不变），同宏任务内后续调用合并为
   一次补播（setTimeout(0) 解锁，不依赖 director 暂停状态）——多助手/狂暴同帧多次
   全量广播（sync/layoutBar/LocLabel×N）从 N 次降到 2 次。
5. **瓶盖预制体** `Prefabs/Game/Cap`（build_cap_prefab.py，Sprite=capchip_0 40×36，
   check_prefab 通过）+ Prefabs 清单；CapMachine.ensurePool 优先 Prefabs.make 实例化、
   未加载兜底 nd()。**池节点仍常驻 chips 容器只切 active，不走通用 Pool.acquire/release**
   （后者每次 removeFromParent/addChild 重建合批，对每帧更新的实体反而更慢——这是
   「高频常驻实体」与「一次性借还对象」两种池化的选型区别）。

**回答口径**：文字层合批=已合批（drawcall 47），但系统字体 Label 每实例独立纹理、
无法跨 Label 合批——当前 Label 数量少不构成瓶颈；若未来 Label 上百，方向是 BMFont
或「数字图集 Sprite 拼字」。剩余可做：履带瓶盖节点数 110→64、Label cacheMode=BITMAP
（静态文字免每帧重排）、数字图集。
