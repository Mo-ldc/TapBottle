## 第八十二轮（2026-09-29 晚）：「瓶子多会卡」性能归因 —— 动画洗清嫌疑

用户反馈瓶子太多卡顿，怀疑动画。做了三轮无头实测（`_q81_perf.tpl` / `_q82_perf2.tpl` /
`_q83_drawcall.tpl`，探针 = director 四事件插桩 logic/draw 分段 + cc.profiler 读 draws/tricount）：

- **规模扫描**：1/40/100/150/300 瓶 → JS 逻辑 0.20→0.33ms/帧（几乎平）；帧间隔 55→73ms 线性涨
  （每瓶 ~0.06ms，150 瓶 +8.7 / 300 瓶 +17.7 严格线性）；节点数 282→1179（每瓶 3 节点 2 精灵）。
- **决定性消融**：300 瓶把 600 个精灵全部 `active=false` → 帧耗**立刻回到 1 瓶基线**（54.9ms）。
  → 卡顿 100% 来自精灵绘制，与 JS/动画无关。
- **动画单独压测**：100 瓶每帧全翻（rAF 循环不停 flip）→ logic 只 0.91ms/帧。tween 创建 1.3µs/条。
- **draw call 恒定**：1 瓶 39 个 → 300 瓶 38 个（动态图集把 7 阶瓶身+影子全合进同批次）；
  tricount 688→1882 线性。混阶/同阶无差异 → 合批不是因素。
- **成本结构**：只留瓶身 +11.5ms / 只留影子 +5.4ms —— 影子面积只有瓶身 2.7% 却占 31% 成本
  → **固定开销（顶点/变换/提交）主导，面积（overdraw）次要**（半尺寸面积 1/4 也只省 48%）。
- 单次基准（n=100）：doSort 0.025ms、pickSpot 0.06ms、hitTest 0.0005ms、sync 建 100 瓶 8.2ms（一次性）。
- 资产事实：瓶身贴图实为 58×145~74×167（显示放大到 150×375）；无 .pac 自动图集；
  **构建一直是 `debug:true`**（引擎带检查，真机 release 会快不少）——发版前务必 `debug=false` 重构建。

结论：不是动画问题；是「同屏精灵数量」的渲染成本。优化方向按性价比：①同屏渲染预算
（超限隐藏影子或简化表现）②发版用 release 构建 ③真机复测（探针可复用）。
